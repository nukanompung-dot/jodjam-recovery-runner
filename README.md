# Encrypted recovery job — code only

This repository contains capture-job code and synthetic tests only. It contains no application, database schema/provisioning, restore tool, runtime configuration, credentials, private key, real identity, receipt, archive, or learner data. Publication and operational changes belong only to the authorized human publisher. No workflow can push or deploy application code.

Run the secret-free checks with Node 24:

```sh
node scripts/security/verify-export-manifest.mjs
node --test scripts/recovery/unit.test.mjs scripts/security/verify-ci-protection.test.mjs scripts/security/verify-export-manifest.test.mjs
```

`public-runner-manifest.json` fixes the exact inventory and SHA256 of every exported file plus its reviewed source commit. New or changed files require a fresh reviewed export. Do not copy a working tree, git history, `.env`, SQL, app code, restore code or recovery files here. The code license is not expanded by this packaging operation.

## Operator setup — schedule OFF

The backup workflow has **no schedule trigger**, defaults to manual preflight, and keeps `RECOVERY_READY` off. Do not enable it from an unprotected branch or put cloud/runtime credentials into repository secrets. Initial publication, protection setup and any later schedule change are separate deliberate operator actions.

1. Publish only this reviewed package into a new **public** dedicated repository with default branch `main`. Keep the application repository private. Inspect collaborators, integrations, forks and Actions settings; permit only trusted reviewers/operators. The package itself does not create a repository or push anything.
2. Set classic main protection: enforce administrators, at least one independent approving review, dismiss stale approvals, require approval after the latest push, strict up-to-date required check `public-runner-tests` bound to the official GitHub Actions App (ID 15368), no PR bypass users/teams/apps, no force pushes and no deletions. Use independent trusted reviewers. CODEOWNERS coverage can add protection but is not a substitute for the independently checked PR-review baseline.
3. Create `security-backup` **before** any credential-bearing job references it. Select deployment branches/tags with exactly `main` as a branch; allow no tags/wildcards. No required-reviewer/custom-app gate is assumed for unattended operation. Inspect and disable administrator environment bypass in the owner UI; REST omission is not proof. Audit inherited rulesets separately: they cannot weaken the mandatory classic baseline, and public rules APIs hide bypass actors without additional access.
4. Create a dedicated expiring fine-grained PAT selected **only for this public helper repository** with Administration **read** plus automatic Metadata **read**; no Contents, Actions or any write/cloud permissions. Store only this limited audit token as repository secret `RECOVERY_PROTECTION_READ_TOKEN`. Never use the publisher's broad `gh` credential or a write token. The ordinary `GITHUB_TOKEN` is not a fallback. Public repository/branch/environment metadata is read without authentication; only classic protection receives the audit PAT.
5. Review the exact public `main` SHA and actual settings, token scope, code ownership/reviewer access and hidden admin-bypass settings. Record repository variables `RECOVERY_POLICY_REVIEWED_SHA` and `RECOVERY_POLICY_REVIEWED_AT` (UTC ISO time). This is separate human evidence, not a machine claim about hidden fields. It expires after 30 days and must match the current main SHA. Repeat it after every publication/settings change. This cannot defend against an owner who deliberately changes both policy and code.
6. Put **all runtime values and identifiers** in protected **environment secrets**, including `RECOVERY_APP_ORIGIN`, `RECOVERY_SOURCE_PROJECT_REF`, `RECOVERY_RUNNER_SECRET`, `RECOVERY_DRIVE_TARGET_JSON`, `RECOVERY_DRIVE_CLIENT_ID`, `RECOVERY_DRIVE_CLIENT_SECRET`, `RECOVERY_DRIVE_REFRESH_TOKEN`, `RECOVERY_DATABASE_URL`, `RECOVERY_DATABASE_CA_BASE64`. Never put them in public YAML, repository variables, logs or artifacts. Public stdout is deliberately generic. No restore/age private identity belongs on this runner.
7. Review backend authorization, dedicated verified-TLS read-only database access, metadata scope coverage, dedicated exact `drive.file` OAuth, correct private archive owner/folder, inaccessible private recovery key and verified recipient recovery. Run manual **preflight** only after actual server settings can be read. API denials/schema changes/timeouts fail closed; no automatic plan purchase or elevated credential fallback occurs.
8. Complete a separate isolated real capture/restore drill, alerts and key-custody review. Health returns early-stale warning at 18 hours and critical at 24 hours; both fail the job with content-free logs. Manual `health` mode uses only gateway authority, no database/Drive credentials. Configure the actual GitHub failure-notification recipient and independently verify delivery for warning and critical failures before READY; a console annotation is not delivered notification evidence. Keep recipient addresses and delivery evidence out of this public repository. Only then may the operator set `RECOVERY_READY=true`, run a deliberate capture, and propose a reviewed schedule change for capture every 12 hours plus independent health every hour. The exported workflow contains no cron triggers; the existing job guards accept only `7 * * * *` for gateway-only hourly health and `17 */12 * * *` for capture. Adding those cron triggers is a reviewed later change with the same main/environment gates. A passing code test or policy inspection does not establish hosted backup readiness, a production RPO/RTO, alert delivery, or a successful real restore. Keep schedules off until that evidence exists.

Public CI runs synthetic local HTTP tests without production secrets or external provider calls. Capture jobs check out the event's exact SHA, not a moving main reference. No artifact-upload step exists. Runtime receipts, paths, project identifiers, database diagnostics and object counts are not printed. Existing private recovery tooling and recovery identities remain outside this repository.

GitHub documents PR-bypass actors for organization-owned repositories only. For a personal repository, the classic API may omit `bypass_pull_request_allowances`: the inspector accepts that omission only when the trusted repository response says owner type `User`, its owner login and full name match the exact expected repository, administrator enforcement and every other review/check/environment gate pass. This is a narrowly scoped inference from the documented personal-repository model, not a rule that missing lists are empty. Organization/unknown/mismatched ownership, explicit null/partial lists and every nonempty bypass list are refused. [Protected branch ownership and bypass semantics](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches).

The classic protection endpoint requires [Administration read](https://docs.github.com/en/rest/branches/branch-protection#get-branch-protection). Public [environment](https://docs.github.com/en/rest/deployments/environments#get-an-environment) and [deployment branch policy](https://docs.github.com/en/rest/deployments/branch-policies#list-deployment-branch-policies) reads can be unauthenticated. [Ruleset bypass visibility](https://docs.github.com/en/rest/repos/rules#get-a-repository-ruleset) is limited; omitted ruleset bypass lists remain unknown. [Workflow permissions](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#permissions) have no configurable Administration permission. These documented limits are why policy inspection and owner setup are separate gates.
